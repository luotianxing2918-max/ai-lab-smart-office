# 决策记录

每个会影响成本、体验、安全、施工或后续维护的选择，都应新增一份决策记录。文件名采用 `YYYY-MM-DD-主题.md`，例如 `2026-07-31-iot-vlan-isolation.md`。

## 模板

```md
# ADR-001：决策名称

- 日期：YYYY-MM-DD
- 状态：提议 / 已批准 / 已替代
- 关联 Issue：#编号

## 背景

当前问题、约束与目标。

## 备选方案

1. 方案 A：优点 / 缺点 / 成本
2. 方案 B：优点 / 缺点 / 成本

## 决定

最终选择及原因。

## 影响与回滚

对预算、施工、运维的影响；若失败如何恢复。
```
::: tip
决策记录不追求长篇大论，关键是让半年后接手项目的人明白：当时为什么这样做、影响什么、由谁确认。
:::

# ADR-001: 部署环境监听型上下文感知 AI 助理 (Ambient Context-Aware AI)

- 日期: 2026-07-31
- 状态: 提议
- 关联 Issue: #001

## 背景

**当前问题：** 
传统的智能语音交互（如小爱同学、Siri）采用“一问一答”的 Stateless (无状态) 模式。在真实的办公室商业洽谈中，若遇到需即时查阅的数据，用户必须手动唤醒 AI 并重新复述完整背景，这会严重打断对话心流 (Flow State)，显得极其生硬，无法体现真正的智能化。

**约束：**
1. 隐私与安全底线：不能将客户的全部商业机密对话持续上传至云端。
2. 硬件算力：持续监听与多模态渲染需要强大的边缘节点 (Edge Node) 支持。
3. 交互时延 (Latency)：从发出特殊指令到大屏 (LED Screen) 呈现图表及语音播报，必须控制在极短时间内。

**目标：**
构建一个“沉默的专家”系统。AI 在后台实时转录对话并维持一个短期的 Rolling Context (滚动上下文记忆)。只有当接收到特定的 Trigger Phrase (触发短语，如“回答一下刚刚这个问题”) 时，系统才会锁定记忆池，结合最新问题执行 Web Search (网络检索) 与 Deep Thinking (深度思考)，最终输出 Voice (语音) 加上 Visual Data (视觉化图表/真实数据) 的多模态响应。

## 备选方案

1. 方案 A: 全云端流式处理 (All-Cloud Streaming)
   - 优点：开发成本极低，全靠云端大模型的长上下文能力。
   - 缺点：致命的商业隐私泄露风险；严重依赖外网稳定性，网络抖动会导致响应失败。
   - 成本：持续的高额 API token 消耗。

2. 方案 B: 边缘端记忆池 + 云端按需推理 (Edge Memory Pool + Cloud On-demand Inference)
   - 优点：使用本地算力运行小参数量的 ASR (Automatic Speech Recognition - 自动语音识别) 将对话实时转文本并存在本地内存。只有在听到唤醒词时，才将这一段“文本上下文”打包发送给云端高级 LLM 进行搜索和生成。绝对保障隐私，且响应更高效。
   - 缺点：系统架构复杂，需自行搭建 Event-driven Architecture (事件驱动架构) 以联动 LED 屏幕与语音播报。
   - 成本：初期硬件投入较高（需配置远场麦克风阵列和本地小型服务器）。

**最终选择及原因：**
强烈建议选择 **方案 B**。对于 To-B (面向企业客户) 的场景，Data Privacy (数据隐私) 是不容谈判的底线。边缘端截留原始音频，只上报脱敏文本的策略是唯一合规且专业的打法。同时，这种软硬结合的架构能为你后续的创业项目打下坚实的基础架构模板。

## 影响与回滚

**对预算、施工、运维的影响：**
- **预算：** 需额外采购一套高质量的拾音麦克风阵列 (Microphone Array) 以及驱动 LED 大屏的树莓派或微型主机。
- **施工：** 需对办公室进行简单的声学测试，确保麦克风在降噪和回声消除 (AEC - Acoustic Echo Cancellation) 方面的表现。
- **运维：** 需监控本地转录服务的持续存活状态。

**若失败如何恢复 (Rollback)：**
若本地拾音或上下文打包模块出现严重 Bug 导致无法准确回应，系统应能够平滑降级 (Graceful Degradation) 为传统的“即呼即答”智能音箱模式，不再依赖上下文记忆，由用户直接输入完整提问，确保最基础的查询功能不断线。
